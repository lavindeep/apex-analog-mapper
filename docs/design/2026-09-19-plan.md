# Rewrite implementation plan

Companion to `2026-09-19-rewrite.md` (the design). Working plan for the `claude/rewrite`
branch. Revised after the plan review recorded in `reviews/plan.md`.

## Conventions

- Branch `claude/rewrite`, one PR to `main` at the end. Conventional commits, author
  Lavindeep Dhillon, explicit `git add` paths.
- .NET 10 SDK, portable install at `C:\Users\lavin\Documents\Codex\tools\dotnet`
  (prepended to PATH per shell, never machine-wide).
- `dotnet test -c Release` runs everything that needs no hardware. Hardware tests carry
  `[HardwareFact]`, which skips unless `APEX_HW_TESTS=1`. The 30-minute soak carries
  `[SoakFact]`, which skips unless `APEX_SOAK=1`.
- Nothing in the hook callback, sensor loop, or engine tick allocates. Tests assert
  zero allocations with `GC.GetAllocatedBytesForCurrentThread`, read on the thread
  under test after a warm-up pass.
- Hardware test thresholds live in `tests/ApexMapper.Windows.Tests/HardwareThresholds.cs`
  and are filled from `docs/design/measurements.md` with stated headroom. Stage 7
  checks the two agree.
- `docs/design/requirements.md` lists every design requirement as a numbered line with
  an owning stage and an evidence column (`file:line` plus test name). Trace reviewers
  fill the column; a requirement with no evidence is a gap.

## Gate protocol

At the end of each stage:

1. Findings first. Reviewers run in parallel, each with the design, the plan,
   `requirements.md`, and the stage diff. Each must run `dotnet test -c Release`, paste
   the output, and cite `file:line` for every finding. Findings without a citation are
   discarded. Findings are committed to `docs/design/reviews/stage-N.md` before any fix.
2. Reviewers on every stage: trace (fills the evidence column, lists gaps), failure
   (every thread, lock, handle, and failure path: races, leaks, deadlocks, silent
   swallows), test (names behaviours the tests do not pin). Plus the stage-specific
   reviewer named below.
3. Fixes land in their own commits. A second pass reviews only the fix commits.
4. Hardware tests that apply to the stage run on the maintainer's PC and their output
   is saved under `docs/design/reviews/stage-N/`. Stages with no hardware tests say so.
5. Blockers and highs fixed before the stage closes. Mediums fixed or recorded with a
   reason.

## Stage 1: Core

### Interfaces

Fixed before any file is written. The feel reviewer checks the worked example against
the code.

As shipped after the stage 1 gate (the draft had `GateAll`, a `SourceSelector` with
an at-rest latch, and `Tick(store, snapshot, ...)`; the review record says why each
changed):

```csharp
// Per slot: digital state from the hook, analog depth from the sensor, gate bit, and
// whether the profile drives the slot from the sensor. One packed long per slot.
public sealed class KeyStateStore
{
    public void SetDigital(int slot, bool down);        // hook thread
    public void SetAnalog(int slot, float depth);       // engine thread, NaN = unavailable
    public void SetAnalogDriven(int slot, bool on);  public void ClearAnalogDriven();
    public void Gate(int slot);  public void GateUnknown();  public void ClearAll();
    public bool IsGated(int slot);
    public KeySlot Read(int slot);                      // digital, analog, gated, analogDriven
}

// Shared between the poller and the engine. The poller fills a private working
// snapshot and publishes it by copy under a sequence lock.
public sealed class SensorSnapshot
{
    public SensorSnapshot(double ticksPerMs);           // freshness limit derived from FreshnessMs
    public void Begin(long timestampTicks);  public void SetGroup(int group, raw, filtered);
    public void Publish(SensorSnapshot working);
    public bool TryBeginRead(out int generation);  public bool EndRead(int generation);
}

public sealed class Mapper
{
    public Mapper(CompiledProfile profile, KeyStateStore store);  // one per session; claims the analog-driven flags
    public void Tick(SensorSnapshot? snapshot, long nowTicks, float dtMs, ref PadReport report);
    public void ResetState();                            // session start, return from alt-tab
    public bool SnapshotFresh { get; }  public int FallbackCount { get; }
}
```

Tick order per binding:

1. Gate. If the slot is gated, the key's ramp and handover state are reset and the
   key contributes zero; when either key of an axis becomes gated the axis's rate and
   conflict state reset too. `GateUnknown` gates every analog-driven key and every
   digital key that is down. While a key's sensor reading is available only an analog
   reading at rest clears its gate (rapid trigger makes hook key-ups mean "rising");
   while the reading is unavailable, and for digital keys always, any hook event other
   than an auto-repeat clears it.
2. Source. Analog if the key's reading is available this tick: the snapshot is fresh
   (`nowTicks - snapshot.Timestamp` under the fixed `SensorSnapshot.FreshnessMs` of
   60 ms), its group was read, and the key is calibrated. Otherwise digital.
3. Ramp. One ramp per key. While analog drives the key the ramp value is set to the
   depth every tick (so it is always seeded), except on the tick analog takes over
   from digital, when the ramp runs from the fallback value to the live depth at the
   binding's rate (or 50 ms full scale) and passes through once it arrives. While
   digital drives an analog key the ramp integrates toward 0 or 1 at the binding's
   rate, or at the fallback rate if the binding's rate is zero. Buttons skip the ramp
   and the response entirely: they are pressed when the hook says down.
4. Deadzone and response, for triggers and axis keys.
5. Conflict rule, then axis mode, for axis pairs.
6. Pack. `dtMs` is clamped to 0..50 ms before any of this so a scheduling stall moves
   the output by at most one fallback ramp.

Worked example, W bound to right trigger, press ramp 0, analog held at 0.7: sensor
faults, snapshot goes stale. Tick N: source becomes digital (hook says down), ramp is
seeded at 0.7, target 1.0, fallback rate 50 ms full scale, so the output reaches 1.0
after 15 ms. User releases W: hook key-up, ramp runs to 0 at the fallback rate. Sensor
recovers while W is still held at 0.7: the ramp runs from 1.0 down to 0.7 over 15 ms
and W is analog again. Sensor recovers while W is up: the ramp finishes whatever
descent was in progress and the next press is analog.

Profile changes stop the session; `Mapper` is rebuilt for the next start. There is no
mid-session profile swap.

Digital ownership: the hook owns the store's digital value and gate clearing for
mapped keys. Raw Input is used only for device attribution (the other-keyboard notice)
and for the learn and travel steps. The hook has no device identity, so a key-up from
any keyboard clears the gate; the design records this limitation.

## Stage 3: output and session

Inputs from the stage 2 ledger:

- Self-stop: `StopRequested`, `Timer`, `DeviceChanged` and `Changed` run on the thread
  that owns them, and `Stop()` called from any of them returns false at once; the
  thread exits after the current message. The session must not wait for the hook,
  pump or tracker from their own handlers.
- Hook timer handlers must be cheap and never block; an exception there is counted in
  `HandlerFaults`, not propagated, so the session polls the counter.
- Unhook detection: Windows removes a low-level hook silently on a callback timeout.
  The watchdog compares the hook's `EventCount` against the pump's: raw events arriving
  while the hook's count stands still means the hook is gone; gate every mapped key,
  reinstall, and report.
- `ForegroundTracker.Changed` is wired to `HookPolicy.ForegroundLost` and the store's
  `GateUnknown`, with a test.

Shutdown order on Stop, with the bound per step:

1. Set the stopping flag; disarm the watchdog.
2. Engine: signal the timer, join (bound 50 ms).
3. Pad: zero, disconnect (bound 2 s, the driver's own limit).
4. Hook: `WM_QUIT`, join (bound 500 ms).
5. Sensor: signal the stop handle, `Abort()` the interface, join (bound 500 ms).
6. Raw Input pump and foreground tracker: `WM_QUIT`, join (bound 500 ms each).
7. Restore GC mode.

Hardware tests, each `[HardwareFact]`:

- Loopback: synthetic depth ramp on `LeftStickX` into the engine; XInput sampled with
  the winning timer from another thread; asserts `dwPacketNumber` increments per second
  at or above the threshold file's value while input changes every tick, and p99
  submit-to-readback under floor plus headroom.
- Kill: child harness as in the spike (pad at 255, hook swallowing including injected,
  message pump alive, a different thread blocked); parent terminates it; asserts
  `ERROR_DEVICE_NOT_CONNECTED` on the former index within the threshold and that a
  `SendInput` W reaches the parent's foreground window.
- Wedge: child harness blocks inside a fake submit that never returns; asserts the
  watchdog claims the owner, zeros, and unplugs within the derived bound, and that the
  wedged submit's eventual return does not touch the driver again.
- Soak (`[SoakFact]`): 30 minutes of synthetic input; asserts working set flat within
  10 MB, handle count flat, every key zero at the end, `GC.GetTotalPauseDuration`
  delta under 5 ms per wall-clock second, and `GC.CollectionCount(2)` unchanged.

Stage-specific reviewer: safety reviewer, attacks the "what the game sees" column and
the shutdown order.
