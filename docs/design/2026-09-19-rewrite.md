# Apex Analog Mapper rewrite

Date: 2026-09-19. Status: approved design. Branch: `claude/rewrite`, merges to `main` in one PR.

## Why

The v0.5 alpha on `codex/windows-validation` works but is overbuilt (37k lines, nine
projects, a supervisor process with its own pipe protocol) and the driving feel is wrong.
The rewrite keeps the hard-won hardware knowledge and drops the rest.

Findings from the reference that drive this design:

- The virtual controller updated at 10 Hz. The engine ticked fast, but pad state was
  shipped to the supervisor process on a 100 ms timer.
- Nothing ever ran at the rates the code claimed. No timer resolution was requested, so
  the "1 ms" engine wait and "5 ms" sensor pacing were probably 15.6 ms.
- The shipped racing profile's ramps did nothing (analog bypasses press ramps, release
  ramps were zero), and no feel parameter was editable in the app.
- The calibration layer had a step at the start of travel and could permanently silence
  a key if the sensor's rest reading drifted.

## Product

Read per-key analog depth from a SteelSeries Apex Pro keyboard, map it to a virtual
Xbox 360 controller through ViGEmBus, and block the mapped keys from reaching the game
while the selected game is in the foreground. Primary use is racing games with W and S
as analog throttle and brake and A and D as analog steering. Public GitHub release.

Out of scope for v1: tray icon, login task, hot reload, latency histogram window, log
viewer, anti-cheat and Steam process scanners, benchmarks, WiX MSI, supervisor process,
generic HID descriptor machinery, multi-level backups, automatic profile resolution,
rumble. The "never inject code, never read game memory, never install a filter driver"
stance stays as a README statement and a design constraint.

## Stack

- C# on .NET 10 LTS. (.NET 8 and 9 leave support on 10 November 2026.)
- WPF with the lepoco WPF-UI library for Fluent controls and OS light/dark theme.
- Velopack for the per-user installer, Add or Remove Programs entry, uninstall, and
  delta updates from GitHub Releases. Self-contained publish; the size is stated in the
  README. Releases are unsigned; SHA-256 is published per asset and SmartScreen is
  documented.
- HidSharp for HID, Nefarius.ViGEm.Client for the pad, xunit for tests.
- Rust with Tauri was considered and rejected: the hot path is thin enough that GC is a
  non-issue once it allocates nothing, all native pieces have working C# to port from,
  and the maintainer reads C# more easily than Rust. Electron was rejected because every
  native piece would need a sidecar process.

## Shape

One process, three projects plus two test projects:

| Project | Contents | Tests |
| --- | --- | --- |
| `ApexMapper.Core` | Profile model, calibration math, curves, ramps, conflict rules, key state store, engine tick, JSON documents. No Windows APIs. | Unit tests for every rule. |
| `ApexMapper.Windows` | Raw Input, low-level hook, HID sensor reader, device discovery, ViGEm output, foreground tracking, driver detection, timers. | Unit tests with fakes, plus hardware tests gated by `APEX_HW_TESTS=1`. |
| `ApexMapper.App` | WPF window, view models, settings, Velopack integration, update check. | View model tests. |

### Threads

| Thread | Job |
| --- | --- |
| Raw Input pump | Message-only window with `RIDEV_INPUTSINK` and `RIDEV_DEVNOTIFY`. Attributes digital key events to a physical keyboard, detects arrival and removal. Never blocks anything. |
| Hook | `WH_KEYBOARD_LL` with its own message loop. Swallows mapped keys while the game is foreground. Records down and up per key into a lock-free array. Also runs the watchdog and the stop hotkey. Above-normal priority. |
| Sensor | Polls the keyboard's vendor interface back to back for the groups the profile needs. Publishes a timestamped snapshot. |
| Engine | High-resolution waitable timer at 1 ms. Merges the three sources into the key state store, runs bindings, packs the report, submits to ViGEm when the packed report changed, capped at 500 Hz. Publishes a tick timestamp for the watchdog. |

The hook callback and the sensor and engine loops allocate nothing. The process runs
with `GCSettings.LatencyMode = SustainedLowLatency` while a session is active. The hook
callback reads the `KBDLLHOOKSTRUCT` through a pointer, reads a cached foreground flag,
and never calls into win32k or takes a lock.

### Key state store

One slot per scan code (plain, E0, and E1 pages). A slot holds a value in 0..1, a
provenance (digital or analog), and a gate bit.

A slot holds two values at once, the hook's digital state and the sensor's depth,
because fallback needs both at the same instant.

The gate exists for keys whose physical state is unknown. It is set on: session start,
returning to the game after alt-tab, hook install, keyboard reconnect. While gated, the
key contributes zero and its ramp and handover state are reset (and, for an axis, the
rate and conflict state), so clearing the gate never releases a stale value. An
observed release clears the gate. For a key the profile drives from the sensor, only an
analog reading inside the calibration noise band counts while the sensor reading is
available. While the reading is unavailable (stale, faulted, or not yet read) the hook
is the only evidence there is, and any hook event other than an auto-repeat counts,
exactly as for a key the profile drives digitally. Without that rule a dead sensor at
session start would leave every analog key gated for good.

Rapid trigger is why analog keys cannot trust the hook: with it enabled (the
maintainer's setting, and the default many players use), the firmware sends key-up as
soon as the key rises about 0.1 mm, wherever it is in its travel. A key-up therefore
means "moving up", not "released". The firmware's actuation setting (0.1 mm and up)
likewise decides where key-down fires and has no bearing on the sensor path.

The gate is never set by a sensor fault. The hook knows whether the key is down, so a
sensor fault switches the key to digital fallback instead (below).

The hook owns the digital value and gate clearing for mapped keys. Raw Input only
attributes events to a physical keyboard (for the other-keyboard notice) and feeds the
learn and travel steps. Since the hook has no device identity, a key-up from any
keyboard clears the gate.

### Analog input

Protocol, verified on Apex Pro TKL gen 1 (USB 1038:1614, firmware 4.9.1):

- Vendor interface: usage page 0xFFC0, usage 0x0001, 65-byte input and output reports,
  same Windows container id as the selected keyboard. Non-exclusive open.
- Request: 65-byte output report `[0x00, command, selector, 0...]`. Reply: 65-byte
  input report with byte 0 equal to 0. Replies carry no command echo.
- Command 0x90: firmware version as ASCII at offset 1.
- Command 0xD7 with selector 1..5: one group of 14 sensors. Bytes 1..28 are raw uint16
  LE, bytes 29..56 are filtered uint16 LE, bytes 57..64 are zero. Values are 12-bit.
- Sensor index to scan code table: 70 slots in firmware order, 65 mapped. Arrow keys and
  the function row are mechanical. Ships as the default; the learn step can override it.

Only these two commands are ever written to the vendor interface. The allowlist is
enforced in one place with a test.

Desync defence, because a dropped or foreign reply shifts every later reply by one:

- Every group reply carries a signature: the set of slots that read under 50 counts
  (no key there). Calibration records each group's signature; the poller checks every
  reply against it and any value above 4095. A mismatch means a shifted or foreign
  reply and retires the handle. This costs nothing per cycle.
- A 0x90 canary every 50 cycles, verified against the firmware string. A mismatch
  retires the handle.
- Any fault retires the handle, waits on a signalable backoff, reopens, and
  re-verifies firmware.
- No input-queue drain. Stage 0 measured zero stale replies in 90 s and found the only
  drain HidSharp allows costs 10 ms per call.
- Depth comes from the raw bytes. Stage 0 measured the firmware's filtered values as
  half a sample to one sample (3 to 6 ms) behind raw for a noise gain of ten counts
  on a 3000-count span.

Freshness is a fixed 60 ms: a snapshot older than that is stale and analog keys fall
back to digital. The figure is about five two-group cycles. It is fixed rather than
derived from a rolling percentile because a rolling limit grows with the jitter it is
meant to catch, and it is generous because a false fallback costs a brief dip (the
handover back to analog is a short ramp) that is still better avoided. Faults: a read timeout (150 ms), or three consecutive cycles of 100 ms or more.
A single slow cycle only makes the snapshot stale. The status card shows the measured
p50 and p99 cycle period.

Calibration is stored per physical keyboard (container id) and firmware string. Per key:
rest count, full-press count, noise band, and the sensor index found by the learn step.
The noise band defaults to 20 counts and rises to 1.5 times the peak-to-peak noise
measured at rest during calibration when that is larger.

Clipping: W on the measured board reaches the 4095 ceiling before bottoming out.
Calibration detects a clipping key (full press reads 4095), stores 4095, and tells the
user that the top of that key's travel produces no change. A plateau below the
ceiling cannot be told from bottoming out by value alone, so it is not detected. During a session a key that sits at 4095 for more
than a few seconds is a plausibility warning. Spans differ by up to 18 percent between
keys, so calibration is per key, never shared.

The sensor's count response is compressed near rest: 0.2 mm of travel is 2.5 percent
of the count span. The feel step examines this region specifically, and the response
preview shows counts as well as depth so the compression is visible.
Normalisation re-scales above the noise band so there is no step at the start of travel:
`depth = clamp((|raw - rest| - band) / (|full - rest| - band), 0, 1)`. Readings inside
the band count as released for gate purposes. A firmware change warns and keeps the data.

### Digital fallback

An analog key is driven by sensor depth while the snapshot is fresh and the key is
calibrated. If the sensor path is stale or faulted after a valid start, the key falls
back to the hook's digital state. One ramp per key carries the transition: while analog
drives the key the ramp is set to the depth every tick, so when digital takes over the
ramp starts from the last analog value and integrates toward the digital target at the
binding's rate, or at 50 ms full scale if the binding's rate is zero. When the reading
comes back the key is analog again at once, and the same ramp carries the output from
wherever fallback left it to the live depth at the same rate, so recovery never steps
and never holds the fallback value. (An earlier draft resumed analog only after a
reading at rest; the stage 1 feel review showed that one 60 ms hiccup mid-corner then
held full lock until the key was fully released.) With the key at rest the ramp simply
finishes its descent. The window shows a warning with the reason for as long as
fallback is active.

Fallback is coarse by nature and coarser with rapid trigger: a key held steady reads as
down (full output after the ramp), and a key being modulated produces alternating
key-down and key-up, so the output ramps with the direction of finger movement. It
exists to avoid an interruption mid-race, not to be driven on. The README says so.

Start is refused until every analog key in the active profile is calibrated for the
selected keyboard. The Start button points at the calibration card when disabled.

### Keyboard blocking

Rules carried from the reference: swallow a mapped key only when the game is foreground;
never swallow injected events; a key-up is swallowed only if its key-down was swallowed;
keys physically down when the hook installs are marked passed; Ctrl, Alt, or Win chords
pass through and release held mapped keys; Ctrl, Alt, Win, and F12 cannot be mapped.

Foreground: a `WINEVENT_OUTOFCONTEXT` foreground hook on its own thread resolves the
owning process and updates a volatile flag; the hook thread only reads the flag. When
the game loses foreground, keys whose down was swallowed are marked passed so their
eventual key-up reaches the desktop; nothing is injected. The game is matched by
executable path. If the foreground window belongs to
`ApplicationFrameHost.exe` (Game Pass and Store builds of Forza), the app finds the
`CoreWindow` child and uses its owner. If the game runs elevated the app cannot see its
input and tells the user to run the mapper as administrator.

The hook has no device identity, so mapped keys are blocked on every keyboard. Raw Input
detects a mapped key from a different keyboard and shows a one-time notice. The README
states the limitation.

### Output

ViGEm in-process on the engine thread. Carried verbatim from the reference: atomic
submit (auto-submit off, all channels set, one `SubmitReport`); the connect sequence that
writes `LeftStickX = 1` then zero and loops until `XInputGetState` reads all-zero,
tolerating `Xbox360UserIndexNotReportedException`, with a 2 s timeout; symmetric
+/-32767 sticks, 0..255 triggers, non-finite values to neutral; zero before disconnect.

Safety without a supervisor:

- Process death: Windows closes the driver handle and ViGEmBus unplugs the pad. Stage 0
  showed the pad gone at the first poll after `TerminateProcess` in six trials, and
  the automated kill test repeats the check.
- Wedged process: the hook thread's 50 ms timer checks the engine's tick timestamp. If
  it is older than 200 ms the hook thread claims pad ownership (an interlocked token
  the engine checks before every submit), zeros and unplugs the pad, and uninstalls
  the hook. The same timer checks the pad's XInput slot and reports a controller
  disconnect.
- Unhandled exceptions: an `AppDomain.UnhandledException` handler zeros, unplugs, and
  unhooks before exit. A driver exception on the engine thread stops the session with
  the reason shown.
- Stop hotkey Ctrl+Alt+F12 is handled on the hook thread, not routed through the engine.

The driver check is "present and running", not a version. If missing, the setup card
shows the required version, a button that opens the official release page in the
browser, and re-checks when the window regains focus. The app never downloads or runs
the driver installer. A "present but not started" state is shown distinctly, since that
is what a pending reboot looks like.

### Session

States: Idle, Starting, Running, Paused, Stopping. Events and outcomes:

| Event | Outcome | What the game sees |
| --- | --- | --- |
| Start | Preconditions: keyboard selected, game selected and running, driver running, all analog keys calibrated. Connect pad, install hook, gate all keys. | Pad appears at neutral. |
| Game loses foreground | Pad zeroed, held keys handed back, gate set for the return. Session stays Running. | Keys reach the desktop, pad neutral. |
| Game regains foreground | Mapping resumes. Keys still held stay dead until released once. Status text says so. | Pad neutral until keys are re-pressed. |
| Sensor stale or faulted | Analog keys fall back to digital with a warning. | Continuous input, ramped. |
| Keyboard unplugged | Paused: pad zeroed, hook kept installed, sensor thread waits. Auto-resume on reconnect, gate set. | Pad neutral, mapped keys still blocked. |
| Game exits, controller disconnects, resume from sleep, user Stop, hotkey, app close | Stop: pad zeroed then unplugged, hook removed, keys ungated. | Pad disappears, keyboard normal. |

The game is remembered by executable path and re-resolved on each foreground change,
so a restarted game keeps working. The selected keyboard is persisted. Updates are never
applied while a session is active. Editing the active profile stops the session. The
process runs with `GCSettings.LatencyMode = SustainedLowLatency` from Start to Stop
and restores it on every exit path.

A single rolling text log (1 MB) records session events and faults, never key presses.
One background writer owns the file; the hook, sensor, and engine threads never write
to it directly.

### Profile model

A profile is a name plus bindings. A binding is either one key to a button or trigger,
or two keys to a stick axis. Fields per binding:

- response: exponent, saturation point (the depth at which output reaches full), and
  deadzone (input fraction treated as zero, re-normalised). Presets linear, soft, and
  aggressive are named values of the same three floats.
- press and release ramps in milliseconds (digital keys only, and the fallback ramp).
- for axes: conflict rule, last-input-wins (default) or neutral; and an axis mode,
  position (depth sets stick position) or rate (depth sets how fast the stick moves
  toward full deflection, releasing returns it to centre). Both ship. The default for
  the Forza profile is chosen in the feel step at the end of the window stage, where
  the maintainer drives both back to back.

One Forza profile ships as the default and as the "reset" for custom profiles. Files
are small JSON with a version integer, written atomically with one `.bak`. Data folder:
`%AppData%\ApexAnalogMapper` (the old `ApexMapper` folder is never touched).

### Keyboards

Verified: Apex Pro (0x1610) and Apex Pro TKL (0x1614), gen 1. Other Apex Pro product
ids (0x1628, 0x1630, 0x1632, 0x1642, 0x1644, 0x1646, 0x1640) get the try-it flow:

1. Send 0x90 only. The reply must be printable ASCII matching a version pattern.
   Otherwise stop and offer the capture export.
2. Show a consent that names the risk in plain words before any 0xD7 is sent.
3. Poll all five groups. Reject replies that are all zero, all identical, or that do not
   change when a key is pressed.
4. Run the learn step: "press and hold W", record which sensor moves, repeat per key.
5. Allow calibration and mapping with an "unverified keyboard" banner, and offer an
   export of firmware string, product id, report lengths, and captures for a GitHub
   issue.

The firmware check is a verified list that warns rather than rejects.

### Window

One window, cards top to bottom:

1. Status: Running or Stopped, reason text, Start and Stop, measured cycle period and
   submit rate, warnings (fallback active, unverified keyboard, other-keyboard notice).
2. Keyboard: detected Apex Pro boards, firmware, verified or try-it.
3. Game: visible windows with executable names, remembered last game, elevated warning.
4. Profile: list, bindings editor (key capture, target), response picker with a live
   preview that shows the actual output as the key is pressed.
5. Calibration: one row per analog key with a live bar of the raw reading, Set released
   and Set fully pressed, the learn step, noise at rest.
6. Setup: driver state with the browser button, Steam Input note, "start the mapper
   before launching the game" note, update check with an Update button.

### Install and update

Velopack `Setup.exe`, per-user, no admin. Update check on launch against GitHub
Releases, cached for a few hours, failing silently, never blocking startup. Install
only on click and never during a session. Prereleases off unless a setting enables them.

## Measurements before code (stage 0)

A throwaway console program on the maintainer's PC (kept in `spike/` until the last
stage) measured exchange and cycle timing, raw versus filtered step response, timer
methods, pad readback, hook callback cost, rest noise, travel spans, the digital
actuation point, and process-death behaviour. Results, decisions, and the runs still
open are in `measurements.md`.

## Testing

- Core: unit tests for every rule, including gate versus fallback, transition seeding,
  drift ungating, conflict rules, packing.
- Windows: fakes for the HID stream, hook events, and foreground. Hardware tests gated
  by `APEX_HW_TESTS=1` and run on the maintainer's PC before every stage gate:
  loopback cadence and latency (asserts update rate and p99 delay), kill test, wedge
  test, 30-minute soak (memory, handles, stuck keys, GC pauses).
- CI: GitHub Actions on `windows-latest` builds, runs the non-hardware tests, and
  produces the Velopack package, on every push to `main` and `claude/**` and on pull
  requests. CI does not install ViGEmBus, so the loopback, kill, wedge, and soak tests
  run only on the maintainer's PC.
- Each stage ends with subagent reviews that trace the code against this document, run
  the tests, and audit concurrency and failure paths, with extra reviewers where the
  stage warrants (protocol review for the sensor stage, security review for the hook).
- After the PR opens: Cursor bugbot review, then the maintainer's physical calibration
  and in-game test with a written checklist.
